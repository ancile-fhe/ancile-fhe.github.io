Research prototype · Fully homomorphic encryption

Write the model once. Run it on any FHE stack.

Every FHE compiler wants the model in its own dialect. Ancile gives your PyTorch model to an LLM agent, which rewrites it for the compiler you select. Ancile compiles it, runs it on encrypted data, and sends the compiler's diagnostics back to the agent until the result passes.

The problem

      
One model. Three compilers. Three different programs.

      
These three files compute the same small network on encrypted data. Each compiler needs a different rewrite, and a change of scheme or library means a new one.

A developer has to learn each compiler's rules to move a workload. Ancile moves that work to an agent and checks the result the same way on every target: the same task, the same test inputs, the same accuracy metric.

  






  

    

      
How a run works

      
The compiler's error is the agent's next instruction.

    

    

      
    
        
  1. Describe the task once
    A plain PyTorch model, its weights, calibration inputs, and test inputs. No FHE library in the task.
    2. 
        
  2. Select the target
    --compiler, --scheme, --backend. Ancile rejects a combination that no backend supports, before any work starts.
    3. 
        
  3. The agent writes the conversion
    It gets the compiler's rules and the model source, writes the solution file, and can run the check itself.
    4. 
        
  4. Ancile compiles, encrypts, and measures
    The compiler runs in its own process or Docker container. The FHE outputs are compared with the plaintext model: MAE, precision bits, top-1 agreement, latency.
    5. 
        
  5. Diagnostics go back to the agent
    On a failure, the agent gets the stage, the error, a hint, and the compiler's numbers. It corrects the file and tries again.
    6. 
        
  6. A pass is saved
    The accepted solution, its metrics, and its cost go to solve/<task>/<target>/<agent>/, ready to compare across targets and agents.
    7. 
      

      

        
The check stages for HEIR with BFV

CKKS on HEIR is so accurate because HEIR selected a 45-bit scale. The Orion default uses 26 bits. Concrete ML, BFV, and BGV compute on quantized integers, so their error comes from the quantization. BGV on OpenFHE accepts only a small plaintext modulus for this model, and two squarings double the bits twice, so it cannot reach 1e-2. That is a property of the scheme on this task.

  






  

    

      
Case study

      
An agent finds the limits of BFV in four checks.

      
BFV computes exactly on integers modulo a plaintext modulus t, with no rescaling. The agent must quantize the model: larger scales give a smaller error, but every value must fit in t. A larger t lets larger values fit, but it adds noise.

      
The LLM agent (fhe-loop, Claude Sonnet 5.5) had only the task, the rules, and the checker's feedback. It found both limits and passed on its fourth check, for $0.30.

Who it is for

      
Plug in one part. Compare it against all the others.

      
Each extension point is separate. A new agent, compiler, backend, or task gets the same checks and the same benchmark as the parts that are already there.

    

    

      
tasks/
FHE application developers
Bring a PyTorch model and an accuracy limit. Run it on every target with one flag, and compare error, latency, and cost before you commit to a library.

      
agents/
AI agent researchers
A benchmark with a strict checker: the compiler accepts the code or it does not, and the error is measured. Swap in an agent with --agent package.module:Class and compare tokens, cost, and checks to pass.

      
compilers/
Compiler researchers
Wrap a compiler behind BaseCompiler: compile, run, and report diagnostics. It then runs on the shared tasks next to Orion, Concrete ML, and HEIR.

      
backends/
Systems and hardware engineers
Declare which compiler and scheme combinations a backend executes. The target flags, the error messages, and the benchmark pick it up from that list.

    

  






  

    

      
Quick start

      
Run one task on three compilers.

      
Ancile runs in a conda env. Concrete ML and HEIR run in Docker images, because their pinned dependencies conflict with the env.

      

        
Set up

conda env create -f environment.yml
conda activate ancile
pip install -e ".[dev]"
docker build -t ancile/concrete-ml:1.9.0 docker/concrete
docker build -t ancile/heir:2026.10.1 docker/heir

        
Run with the reference solutions (no LLM), then with the agent

ancile run -t tasks/examples/mlp_square --agent oracle --compiler orion
ancile run -t tasks/examples/mlp_square --agent oracle --compiler concrete
ancile run -t tasks/examples/mlp_square --agent fhe-loop --compiler heir --scheme bfv

      

    

    

      
Extend

      
A compiler is one class.

      
The runner has no compiler-specific code. A compiler gives its prompt, its solution file, its error hints, and one method that compiles and runs.


class BaseCompiler(ABC):
    def name() -> str
    def solution_files() -> list[str]
    def prompt_file(config) -> Path
    def default_target() -> dict
    def hints() -> list[tuple[str, str]]
    def preflight(config) -> None
    def compile_and_run(workspace, task, config,
                        out_dir) -> CompileResult

      
Each run writes its history to runs/<id>/: the resolved config, the agent's trajectory, every compile log, the metrics, and a report.

    

  






  

    

      
Status

      
What works today, and what comes next.

    

    

      
Works today
Six targets on the CPU, PyTorch tasks with one input and one output, an LLM agent and an oracle agent, and a benchmark with one report for each run.

      
Known limits
One example task. The default Orion config cannot bootstrap. The agent loop runs on the host. HEIR's torch-mlir path depends on a pinned nightly wheel.

      
Next
More tasks with bootstrapping and convolutions, swappable compiler passes, GPU backends, and automatic target selection from the constraints.
